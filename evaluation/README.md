# Verdict evaluation

Measures the quality of model output and of the end-to-end verdict without paying
for a model call during ordinary development.

The evaluation never computes a verdict. Every band and score comes from
`buildCompleteAnalysisResult` and `computeVerdict`, the code that serves real
requests. Nothing in `evaluation/` changes a production prompt, schema, model
setting or verdict.

## Modes

| Mode | What runs | Calls a model | Where |
|---|---|---|---|
| Mock | Committed hand-written outputs: the self-test fixtures and the scenario dataset | Never | `npm test` (so also CI), `npm run eval`, `npm run eval:scenarios` |
| Replay | Model outputs recorded earlier, read from a file | Never | `npm run eval:replay` |
| Check references | Validates a human-review reference set. Evaluates nothing | Never | `npm run eval:references` |
| Live | Real calls on the production code path, which also write a recording | Yes | `npm run benchmark` only, with its opt-in phrase and spend cap |

`npm run eval` has no live mode. `EVAL_MODE=live` is refused, a missing recording
is an error, and network access is disabled for the whole run, so the command
cannot fall back to a billable call. Live runs are refused in CI, on Vercel and
with `NODE_ENV=production` (see `benchmark/README.md`).

```bash
npm run eval
```

```bash
npm run eval:scenarios
```

```bash
npm run eval:replay -- --manifest benchmark/cases.json --recording benchmark/results/<file>.recording.json
```

Add `--references <references.json>` to score against references,
`--images <directory>` to check every reviewed image against its recorded hash, and
`--baseline <earlier report>.json` to print what changed against an earlier report.

## Datasets

| Dataset | What it is | Evidence about a model | Command |
|---|---|---|---|
| `selftest` | Nine hand-written fixtures in `evaluation/fixtures/mock/`, several wrong on purpose, with a few synthetic references. Their expected report is a snapshot | None | `npm run eval` |
| `scenarios-v1` | 54 synthetic fashion scenarios in `evaluation/datasets/scenarios-v1/`, each a written brief with a reference output. Compared with a committed baseline | None | `npm run eval:scenarios` |
| `golden-v1` | Real images rated by a person (`evaluation/datasets/golden-v1/`). **Empty until cases are reviewed** | Yes, once reviewed and replayed from a live run | `npm run eval:replay` |

The scenario dataset is generated by `scripts/evaluation/build-scenarios.cjs` (`npm run eval:build-dataset`), which holds the case definitions. Edit the generator, never the JSON; a test fails if they differ.

### What the synthetic datasets can and cannot establish

- **They are synthetic.** No image exists for any case. No model produced any output. The reference outputs are ratings written by hand for a written brief, with explanation text filled in from neutral templates.
- **They can establish** that Verdict's own code behaves as intended on realistic output shapes: schema validation, the deterministic verdict, safety and unsupported-claim screening, uncertainty handling, abstention, and the rule that only ratings move the verdict. They give a fixed reference to detect regressions against when that code, a schema or a check changes.
- **They cannot establish** anything about the quality of a model, a prompt or a recognition result. A 100% pass rate means the reference outputs satisfy the checks, which is how they were written.
- **No measured figures.** Synthetic runs have no latency, token usage or cost. The report shows these as `unavailable`; a value is never estimated.
- `scenarios-v1` has no reference set on purpose: its outputs are the expectations, so scoring them against themselves would measure nothing.

## References and tiers

A reference says what a case is expected to produce. It lives in a reference set
(`verdict-reference-set/1`), a file separate from the manifest, so that adding or
correcting a review does not invalidate a recording that was paid for.

Every reference states its basis and its status, which give its tier. The tiers
are scored in separate sections and never added together.

| Tier | Meaning | Counts as accuracy on real images |
|---|---|---|
| `image_reviewed` | A person looked at the actual image files and rated them | Yes, when the outputs came from a model |
| `brief_derived` | A person derived the expectation from a written brief | No |
| `synthetic` | Written to exercise the evaluation code | No |
| `unreviewed` | A stub or an unfinished review | Never scored |

With no image-reviewed reference, or with hand-written outputs, every
image-grounded figure reads `Unavailable: insufficient human-reviewed ground truth`
(or says that the outputs are fixtures). It never reads 0.

An image review must name a reviewer and a date, a real image source, the right
to use the image, the SHA-256 of every image and all six ratings. A synthetic
expectation may not carry a reviewer. A reference that disagrees with its
manifest (another occasion, other images, a case that does not exist) stops the
evaluation with a list of every problem.

How to add reviewed cases, the rubric and the review template:
[`HUMAN_REVIEW.md`](HUMAN_REVIEW.md).

What a first live run on real images should cover, what it costs at most and
how to read it: [`LIVE_VALIDATION_PLAN.md`](LIVE_VALIDATION_PLAN.md). It is a plan;
no live call is made without approval.

The older `labels.verified` flag and `expected.dimension_ratings` in a manifest
are still read for the legacy "acceptable ratings by confidence" figure. That
flag is a self-declared boolean with no provenance, so it is not evidence of a
human review. Use a reference set instead.

## Per-case checks

Every case gets a status (`pass`, `fail` or `not_applicable`), one result per check, and a reason for each failure. Reasons name dimensions, bands and categories only; they never quote model text.

| Check | Fails when | Kind |
|---|---|---|
| `schema_validity` | A recorded output does not match the current output schema | Blocking |
| `safety` | Screening matches a judgement about appearance, body size, body change, health, age or ethnicity | Blocking |
| `unsupported_claims` | Screening matches a price, label or material claim, or text the case forbids (for example text printed on a tag) | Blocking |
| `uncertainty` | A dimension the case says cannot be seen is rated, or is rated with too much confidence | Blocking |
| `expected_outcome` | A run falls outside the acceptable bands, abstains when it should not, or gives a verdict when it should abstain | Blocking |
| `consistency` | Repeated runs of the same case give different outcomes | Blocking |
| `verdict_integrity` | Recomputing the verdict differs; changing explanations, confidence or the shopping advisor moves the verdict; or an output that states its own verdict is accepted | Blocking |
| `proxy_occasion` | The reason for the occasion rating never mentions the occasion | Proxy |
| `proxy_explanation` | An explanation is very short or very long, or one explanation is reused for different ratings | Proxy |

A case fails when a blocking check fails. Safety failures and schema failures are separate checks, so a report always says which of the two happened.

**Proxy checks are not measurements.** Whether an explanation suits the occasion, or is a good explanation, is a human judgement. The two proxies are rough textual signals that flag a case for a person to read. They never fail a case, never count as a regression, and never touch the production verdict.

## Quality metrics

Four different questions are answered, each on its own. There is no combined
accuracy score, because output validity, agreement with a reviewer, consistency
across runs and the quality of stated confidence are different things.

### Every figure states how far it can be trusted

| Status | Meaning |
|---|---|
| `measured` | Built from at least 10 cases |
| `insufficient_sample` | Built from 1 to 9 cases. The value is shown; nothing may be concluded from it |
| `unavailable` | Nothing to measure. The value is `null`, never 0, with the reason |

A figure carries its value, the number of cases `n` behind it and a standard
error. **The unit is always a case** (for the comparison-group figures, a
group). A case contributes one value to a figure, however many runs, dimensions
or outfit items stand behind it: the share of them that agree. Three runs of one
case, the six dimensions of one case and the items of one outfit are not
independent observations. Counting them as samples would let three cases look
like a measured result, so they are never counted.

The reason attached to an unavailable figure names the actual cause: no
reference of that tier, hand-written outputs, references whose cases produced no
scoreable output, or scored references that hold nothing the figure could be
built from.

### 1. Agreement with references, per dimension

For each of the six dimensions (`occasion`, `color`, `formality`, `seasonality`,
`style`, `style_preference_match`), per tier:

| Metric | Definition |
|---|---|
| Exact agreement | Share of cases whose rating equals the reference rating |
| Within one band | Share of cases whose rating is the reference rating or the neighbouring band |
| Mean absolute error | Mean distance in bands, over cases where both sides gave a rating |
| Coverage | Referenced cases that produced ratings at all, out of all referenced cases |

Excellent, Good, Fair and Poor are four bands, one step apart. "Unable to
Evaluate" is not on that scale. It agrees only with itself. Against a rating it
is a disagreement with no distance, so it lowers both agreement rates and is left
out of the mean absolute error. A case with no valid output lowers coverage, not
agreement.

### 2. Explanation grounding (proxy)

Compares the words of the explanation with the facts a reviewer listed.

| Metric | Definition |
|---|---|
| Key fact mention rate | Share of `key` facts with at least one of their terms in the explanation (supported claims) |
| Supporting fact mention rate | The same for `supporting` facts |
| Mention rate by attribute | The same, split by `garment`, `colour`, `pattern`, `fit`, `occasion`, `other` |
| Cases missing key facts | Cases where a `key` fact is mentioned in no run (listed by id) |
| Contradiction rate | Share of cases whose explanation uses a word listed as contradicting a fact |
| Unverifiable claim rate | Share of cases whose explanation states a detail the reviewer marked as not visible (unsupported claims) |
| Uncertainty handling rate | Where the reviewer said a dimension cannot be judged: how often the model left it unrated or stated Low confidence |

Overconfident claims are reported under confidence (below). Price, label and
material claims, and text a case forbids, are counted by the existing screening.

**This is a proxy and is labelled as one everywhere.** It matches whole words.
It cannot tell "navy" from "not navy", it misses a paraphrase the reviewer did
not list, and a contradicting word may legitimately describe something else in
the picture. It finds cases worth reading. It does not prove an explanation true
or false. The plain-text `expected.key_facts` of a manifest are for a reviewer
and are not scored; only the facts of a reference are.

### 3. Confidence calibration

| Metric | Definition |
|---|---|
| Distribution | How many ratings were stated at High, Medium and Low confidence |
| Agreement by confidence | Exact and within-one agreement among the ratings stated at each level. A case that stated a level at least once contributes one value to it |
| High-confidence error rate | Share of High-confidence ratings that differ from the reference |
| High-confidence severe error rate | Share of High-confidence ratings two or more bands off, or rating what the reviewer said cannot be judged (overconfident claims) |
| Confidence gap | Exact agreement at High minus exact agreement at Low. Positive when confidence carries information |
| Ordering | `consistent`, or `inverted` when a lower level agrees more often than a higher one by more than the noise margin |

The model states High, Medium or Low, not a probability. No probability is
assigned to those labels here, so no expected calibration error is reported: it
would depend on numbers nobody defined. The gap and the ordering need at least 10
cases in each level they compare; below that they are
`insufficient_sample` and make no claim. Stability by confidence (how often a
rating repeats across runs) needs no reference and is reported next to them.

### 4. Image modes

Cases are grouped by garment mode: `single`, `same_garment_views`, `outfit_items`.

| Metric | Definition |
|---|---|
| Valid output rate per mode | Share of runs that returned an output matching the schema |
| Rating stability per mode | Share of dimensions that got the same rating on every repeated run |
| Agreement per mode | Exact agreement, pooled over the six dimensions of each case. For comparing modes only |
| Outfit completeness | Share of complete outfit runs with exactly one valid note per garment image |
| Unexpected notes | Complete runs of the other modes that returned per-item notes |
| Garment type accuracy | Per outfit case, the share of its items whose `garment_type` equals the reference |
| Cross-mode consistency | For cases in one `comparison_group`: share of dimensions rated the same by every case of the group |
| Mean band shift | Mean spread in bands between the cases of a group |
| Several photos against one | Exact agreement of the multi-image cases minus that of the single-image cases of the same group |
| Rating stability per dimension | Share of repeated cases that got the same rating on every run |

### What cannot be measured yet

| Wanted | Why not |
|---|---|
| Colour identification | The output has no colour field. Covered only by the grounding proxy, through key facts with attribute `colour` |
| Pattern identification | The output has no pattern field. Covered only by the grounding proxy |
| Garment identification for a single garment or for views | The output names a garment type only for the items of an outfit |
| Contradictions between views | One output is returned for all views, so views cannot be compared with each other. Only the ratings of cases in one comparison group can |

Adding these needs a change to the model output schema and the prompt, which is
a product decision outside this framework.

## Regressions and the baseline

`evaluation/baselines/scenarios-v1.json` is a complete report committed on purpose. `npm run eval:scenarios` and the test suite (`tests/evaluation/scenarioEvaluation.test.ts`, so also CI) compare the current result with it and fail on a regression.

### Case level

| Classification | Meaning |
|---|---|
| Newly failing | A case that did not fail in the baseline fails now |
| Fixed | A case that failed in the baseline passes now |
| Safety, unsupported-claim, schema, uncertainty, verdict integrity regression | That check went from not failing to failing for a case |
| Consistency change | The consistency result of a case changed, in either direction |
| No longer judged, removed | A case lost its checks or left the dataset; treated as a regression |

### Metric level

Every figure has a stable name in the report's `metric_index` and a direction
(higher or lower is better). Each is classified against the baseline:

| Classification | Meaning |
|---|---|
| `improvement` | Moved in the good direction by more than the noise margin |
| `no_meaningful_change` | Moved by no more than the noise margin |
| `regression` | Moved in the bad direction by more than the noise margin |
| `inconclusive` | There is a figure on both sides, but it supports no conclusion: fewer than 10 cases on either side, a partial run, a different dataset, or (for figures that depend on references) a different reference set |
| `unavailable` | One side has no figure |

**A lost figure counts as worse.** A metric that was measured in the baseline
and has no measured figure now, on the same dataset and references, is listed as
*lost*. It is treated like a regression: the run fails and the baseline cannot
be replaced without the explicit phrase. Otherwise an output that stops
producing something, for example the per-item notes of an outfit, would make its
own metric disappear and pass.

**What the metric gate cannot do.** When the manifest or the reference set
changed, the figures of the two reports are not comparable. They are classified
`inconclusive`, the comparison says how many were not compared, and the change
is judged at case level only. And a figure built from fewer than 10 cases never
produces a regression: in `scenarios-v1` that covers both multi-image modes (3
multi-view cases, 2 outfit cases), which are protected by the per-case checks
and not by the metric gate.

**Noise margin.** The larger of a fixed floor and 1.96 standard errors of the
difference: `max(floor, 1.96 * sqrt(se_base^2 + se_candidate^2))`. The floor is
0.05 (5 percentage points) for a rate and 0.25 bands for a mean absolute error.
For a rate the standard error is `sqrt(p * (1 - p) / n)`. For a mean it is the
sample standard deviation divided by `sqrt(n)`. The floor matters when both
standard errors are near zero, as with a rate of 1.0 on few cases.

The margin treats the two reports as independent samples of cases. They are
the same cases evaluated twice, so the true noise is usually smaller, and
because every figure counts cases the sample is never inflated by repeated
runs. The test therefore leans towards calling a real change "no meaningful
change" over calling noise a regression. The thresholds are constants in
`quality.ts` (`MIN_SAMPLE`, `NOISE_FLOOR_RATE`, `NOISE_FLOOR_BANDS`, `NOISE_Z`)
and are written into every report.

### Replacing the baseline

The baseline is replaced only by an explicit command:

```bash
npm run eval:baseline
```

That command refuses to write the baseline when:

- the run was partial (filtered by case, category or scenario): always refused;
- the recording was made for a different dataset than the manifest: always refused;
- the new report is worse than the current baseline, at case level **or at metric level** (a regressed or a lost metric), unless the decision is stated explicitly:

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --update-baseline --accept-regressions I_ACCEPT_A_WORSE_BASELINE
```

A baseline is never changed as a side effect of running an evaluation or a test.
The test suite also fails when the committed baseline is not byte-identical to
what the code produces from the committed dataset, so every baseline change is a
reviewed diff. (The prompt version recorded in a report is the one the baseline
was written with; the comparison reads it from the baseline, so editing a prompt
does not by itself make this test fail.)

**After a change to the report format** (a new metric, a renamed field), the
baseline no longer matches byte for byte. Run `npm run eval:baseline`, check
that the diff contains only the intended additions, and commit the baseline on
its own. The command still refuses if anything got worse. A baseline in an
older format still compares case by case; its metric-level comparison reads
`unavailable` until it is refreshed.

## Run records

A report is deterministic: the same inputs give the same bytes. A run id or a
timestamp would break that, so they are never written into a report.

Each run writes a separate record to `evaluation/reports/runs/` (git-ignored):

| Field | Content |
|---|---|
| `run_id`, `started_at`, `finished_at`, `duration_ms` | A UUID and the wall-clock times of the run |
| `execution_mode`, `outputs` | `mock` or `replay`; hand-written fixtures or model outputs |
| `code_version` | The Git commit the evaluation ran on |
| `dataset` | Id, version (from the reference set), manifest fingerprint, reference fingerprint |
| `model`, `reasoning_effort`, `prompt_version`, `schema_version` | What was evaluated, plus the versions of the code that evaluated it |
| `cases` | In the dataset, evaluated, successful (every scored run valid), passed, failed, not applicable |
| `latency`, `tokens`, `cost_micro_usd` | Measured values, or `null` when the recording holds none |
| `report` | The report file and the SHA-256 of its bytes |
| `baseline` | The baseline file, its SHA-256, its dataset fingerprint and format |
| `outcome` | `no_regression`, `regression`, `baseline_replaced`, `baseline_refused` or `no_baseline` |
| `comparison` | Newly failing cases, metric regressions and improvements, counts of inconclusive and unavailable |

## Reading a report

Reports go to `evaluation/reports/` (git-ignored) as JSON with sorted keys and
no timestamps or model text, plus a Markdown summary. The summary is ordered as
the questions a reader has:

1. What was evaluated (model, prompt version, schema version, fixture or model outputs)
2. Dataset and references (fingerprints, version, cases per tier, who reviewed)
3. Output validity (valid rate, error codes, latency and cost when measured)
4. Cases (passes, failures and their reasons)
5. Agreement with human-reviewed references, per dimension
6. Agreement with other expectations, labelled as not accuracy
7. Confidence
8. Image modes
9. Explanation grounding (proxy)
10. End-to-end and application results
11. What is unavailable, and why
12. What to do next

The runner appends "Compared with the baseline" to the Markdown file when there
is one. That part depends on the baseline, so it is not in the JSON report.

- A mock report checks the harness and the verdict code. It says nothing about model quality.
- Verdict band agreement is not recognition accuracy: a model can reach an acceptable band for the wrong reasons.
- Results describe one model, one prompt version and one dataset.

### Comparing two models or two prompt versions

Record each one with a separately approved live run on the same manifest, replay
both with the same reference set, and pass one report as `--baseline` for the
other. The comparison covers the valid output rate, per-dimension agreement,
rating stability, confidence calibration, grounding, image modes, and (in the
run records) latency, tokens and cost. The production model setting is not
changed for this: the benchmark takes the model as an option.

## Running part of a dataset

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --cases sc-office-tailored-blazer,sc-wedding-reception-hoodie
```

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --scenarios wedding,party
```

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --categories insufficient_input
```

Filters of different kinds combine with AND. A filter that names nothing in the dataset is an error. A filtered run is marked `partial` in the report and in its file name, can never replace a baseline, and no metric comparison draws a conclusion from it: a figure present on both sides is `inconclusive`, and one missing on either side is `unavailable`.

## Cost and approval

| Action | Cost | Approval |
|---|---|---|
| `npm test`, `npm run eval`, `npm run eval:scenarios`, `npm run eval:replay`, `npm run eval:references` | None. No network access | None |
| `npm run benchmark` without the opt-in phrase (dry run) | None. Prints the worst-case cost | None |
| `npm run benchmark` with `BENCHMARK_LIVE=I_ACCEPT_OPENAI_CHARGES` and `BENCHMARK_MAX_USD` | Billable | Explicit approval for that run. Hard cap $10 |

Worst-case reservation per call, from the pricing table in
`lib/services/openai/modelConfig.ts` (`gpt-6.1-terra`: 8,000 text tokens, 3,600
per image, 4,000 output tokens, $1 and $5 per million):

| Garment images | Images sent | Worst case per call |
|---|---|---|
| 1 | 2 | $0.0352 |
| 2 | 3 | $0.0388 |
| 3 | 4 | $0.0424 |

Sixty cases at three runs cost at most $7.63 even if every case has three
garment images, which is inside the $10 hard cap. These are upper bounds used
to reserve budget, not expected spend, and they follow the configured pricing.
Check the provider's current prices before a live run. The dry run prices each
case at its own number of images.

Latency and cost are reported only when measured: the recording must contain real model outputs with a timing above zero or reported token usage. For synthetic fixtures both are `unavailable`.

## Privacy rules

- Use only synthetic images, images under a licence that allows this use, photos you own, or photos from volunteers who approved this use. Never customer photos.
- Images are never committed. They live under `benchmark/data/`, which is git-ignored; a test fails if an image is tracked under `evaluation/` or `benchmark/`.
- A recording never contains images, file names, prompts or credentials.
- Model text is stored only for cases whose `source` is `synthetic` or `public_license`. For `owned` and `approved_volunteer` cases the output is withheld, because it describes a real person; those runs are counted as withheld and not scored in replay. As decided on 2026-11-17, only `public_license` cases are scored for now (see `HUMAN_REVIEW.md`, "Decisions").
- Recordings of real model outputs stay local (`benchmark/results/` and `evaluation/recordings/` are git-ignored). Review one before committing it.
- A reference describes garments and never a person. A reviewer is named by a short identifier.
- Reports contain aggregates, case ids, reviewer identifiers and verdict bands only.
