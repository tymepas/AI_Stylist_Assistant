# Verdict evaluation

Measures the quality of model output and of the end-to-end verdict without paying
for a model call during ordinary development.

## Three modes

| Mode | What runs | Calls a model | Where |
|---|---|---|---|
| Mock | Committed hand-written outputs: the self-test fixtures and the scenario dataset | Never | `npm test` (so also CI), `npm run eval`, `npm run eval:scenarios` |
| Replay | Model outputs recorded earlier, read from a file | Never | `npm run eval` with `EVAL_MODE=replay` |
| Live | Real calls on the production code path, which also write a recording | Yes | `npm run benchmark` only, with its opt-in phrase and spend cap |

`npm run eval` has no live mode. `EVAL_MODE=live` is refused, a missing recording
is an error, and network access is disabled for the whole run, so the command
cannot fall back to a billable call. Live runs are refused in CI, on Vercel and
with `NODE_ENV=production` (see `benchmark/README.md`).

```bash
npm run eval
```

```bash
EVAL_MODE=replay EVAL_CASES=benchmark/cases.json EVAL_RECORDING=benchmark/results/<file>.recording.json npm run eval
```

Add `EVAL_BASELINE=<earlier report>.json` to print what changed against an earlier report.

## Datasets

| Dataset | What it is | Command |
|---|---|---|
| `selftest` | Nine hand-written fixtures in `evaluation/fixtures/mock/`. Several are wrong on purpose, to prove that the metrics and checks notice. Their expected report is a snapshot. | `npm run eval` |
| `scenarios-v1` | 54 synthetic fashion scenarios in `evaluation/datasets/scenarios-v1/`, each a written brief with a reference output. Compared with a committed baseline. | `npm run eval:scenarios` |

The scenario dataset is generated by `scripts/evaluation/build-scenarios.cjs` (`npm run eval:build-dataset`), which holds the case definitions. Edit the generator, never the JSON; a test fails if they differ.

### What the scenario dataset can and cannot establish

- **It is synthetic.** No image exists for any case. No model produced any output. The reference outputs are ratings written by hand for a written brief, with explanation text filled in from neutral templates.
- **It can establish** that Verdict's own code behaves as intended on realistic output shapes: schema validation, the deterministic verdict, safety and unsupported-claim screening, uncertainty handling, abstention, and the rule that only ratings move the verdict. It gives a fixed reference to detect regressions against when that code, a schema or a check changes.
- **It cannot establish** anything about the quality of a model, a prompt or a recognition result. A 100% pass rate means the reference outputs satisfy the checks, which is how they were written. Model quality needs recorded model outputs (replay), which needs an approved live benchmark run.
- **No measured figures.** Synthetic runs have no latency, token usage or cost. The report shows these as `unavailable`; a value is never estimated.

## Per-case checks

Every case gets a status (`pass`, `fail` or `not_applicable`), one result per check, and a reason for each failure. Reasons name dimensions, bands and categories only; they never quote model text.

| Check | Fails when | Kind |
|---|---|---|
| `schema_validity` | A recorded output does not match the current output schema | Blocking |
| `safety` | Screening matches a judgement about appearance, body size, body change, health, age or ethnicity | Blocking |
| `unsupported_claims` | Screening matches a price, label or material claim, or text the case forbids (for example text printed on a tag) | Blocking |
| `uncertainty` | A dimension the case says cannot be seen is rated, or is rated with too much confidence | Blocking |
| `expected_outcome` | A run falls outside the acceptable bands, abstains when it should not, or gives a verdict when it should abstain | Blocking |
| `consistency` | Repeated runs of the same case give different outcomes | Blocking |
| `verdict_integrity` | Recomputing the verdict differs; changing explanations, confidence or the shopping advisor moves the verdict; or an output that states its own verdict is accepted | Blocking |
| `proxy_occasion` | The reason for the occasion rating never mentions the occasion | Proxy |
| `proxy_explanation` | An explanation is very short or very long, or one explanation is reused for different ratings | Proxy |

A case fails when a blocking check fails. Safety failures and schema failures are separate checks, so a report always says which of the two happened.

**Proxy checks are not measurements.** Whether an explanation suits the occasion, or is a good explanation, is a human judgement. The two proxies are rough textual signals that flag a case for a person to read. They never fail a case, never count as a regression, and never touch the production verdict. Cases may also carry `review` questions for the reviewer.

The verdict is never computed by the evaluation. Every band and score comes from `buildCompleteAnalysisResult` and `computeVerdict`, the code that serves real requests.

## Regressions and the baseline

`evaluation/baselines/scenarios-v1.json` is a complete report committed on purpose. `npm run eval:scenarios` and the test suite (`tests/evaluation/scenarioEvaluation.test.ts`, so also CI) compare the current result with it and fail on a regression.

| Classification | Meaning |
|---|---|
| Newly failing | A case that did not fail in the baseline fails now |
| Fixed | A case that failed in the baseline passes now |
| Safety, unsupported-claim, schema, uncertainty, verdict integrity regression | That check went from not failing to failing for a case |
| Consistency change | The consistency result of a case changed, in either direction |
| No longer judged, removed | A case lost its checks or left the dataset; treated as a regression |

The baseline is replaced only by an explicit command:

```bash
npm run eval:baseline
```

That command refuses to write the baseline when:

- the run was partial (filtered by case, category or scenario): always refused;
- the recording was made for a different dataset than the manifest: always refused;
- the new report is worse than the current baseline, unless the decision is stated explicitly:

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --update-baseline --accept-regressions I_ACCEPT_A_WORSE_BASELINE
```

A baseline is never changed as a side effect of running an evaluation or a test. The test suite also fails when the baseline is out of date in the other direction (a fixed or added case), so every baseline change is a reviewed diff.

## Running part of a dataset

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --cases sc-office-tailored-blazer,sc-wedding-reception-hoodie
```

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --scenarios wedding,party
```

```bash
node scripts/evaluation/run-eval.cjs --dataset scenarios-v1 --categories insufficient_input
```

Filters of different kinds combine with AND. A filter that names nothing in the dataset is an error. A filtered run is marked `partial` in the report and in its file name, and can never replace a baseline.

## Latency and cost

Reported only when measured: the recording must contain real model outputs with a timing above zero or reported token usage. Cost is computed from recorded token usage with the production pricing table; no call is made. For synthetic fixtures both are `unavailable`.

## How the pieces fit

1. A live benchmark run writes `<timestamp>-<model>-<effort>.recording.json` next to its results. The recording stores each case's model JSON with the model, reasoning effort, prompt version, schema version and a fingerprint of the manifest.
2. Replay validates every recorded output against the current schema, computes the verdict with the production verdict code, and scores the result.
3. The report is JSON with sorted keys and no timestamps or model text, so two reports can be compared with an ordinary diff. A Markdown summary is written next to it.

Reports go to `evaluation/reports/` (git-ignored). Commit a report deliberately when it should be kept as a baseline.

## Privacy rules

- Use only synthetic images, images under a licence that allows this use, photos you own, or photos from volunteers who approved this use. Never customer photos.
- A recording never contains images, file names, prompts or credentials.
- Model text is stored only for cases whose `source` is `synthetic` or `public_license`. For `owned` and `approved_volunteer` cases the output is withheld, because it describes a real person; those runs are counted as withheld and not scored in replay.
- Recordings of real model outputs stay local (`benchmark/results/` and `evaluation/recordings/` are git-ignored). Review one before committing it.
- Reports contain aggregates, case ids and verdict bands only.

## Metrics

| Group | Metric | Needs labels |
|---|---|---|
| Model | Valid structured output rate, error codes | No |
| Model | Abstention precision, recall and false abstention rate | `expected.should_abstain` |
| Model | Stability across repeated runs: same outcome, band flips, per-dimension rating agreement, score range | No |
| Model | Confidence: distribution, and how often a rating is stable at each stated confidence | No |
| Model | Confidence: how often a rating is acceptable at each stated confidence | Verified `expected.dimension_ratings` |
| Model | Screening hits for prohibited statements and forbidden claims (confirm by review) | `expected.forbidden_claims` |
| Model | Attribute accuracy (garment, colour, pattern) | Not available: the output has no such fields yet |
| End to end | Verdict band agreement | `expected.acceptable_bands` |
| End to end | Adversarial runs outside acceptable bands; outcome change against the clean twin | `twin_of` |
| Application | Recomputing the verdict from the same ratings gives the same result | No |

Model metrics describe the model's output. Application metrics describe Verdict's own deterministic code. End-to-end metrics depend on both, so a change in either can move them. Prompt and model versions are compared by replaying two recordings of the same manifest and comparing the reports.

Every rate is `null` when there is nothing to measure.

## What a report does and does not show

- A mock report checks the harness and the verdict code. It says nothing about model quality.
- Verdict band agreement is not recognition accuracy: a model can reach an acceptable band for the wrong reasons.
- Results describe one model, one prompt version and one dataset. A small dataset gives wide error margins; treat differences of a few cases as noise.

## Labels

A case may set `garment_mode` (`single`, `same_garment_views` or `outfit_items`) with one or two `extra_garments`; the number of images must fit the mode. It may also state `expected.uncertainty`, `expected.must_be_rejected`, `expected.occasion_terms` and `review` questions for a human reviewer.

A case may carry `labels` (`garment_category`, `colour_family`, `pattern`, `formality`, `expected_uncertainty`) and `expected.dimension_ratings`. Labels describe what is visible in the case's images. They must be assigned by a person looking at those images, not copied from the brief the image was made from, and are scored only when `labels.verified` is `true`.
